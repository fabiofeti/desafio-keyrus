# ADR-001 — Monólito modular, isolamento de dados e mensageria

**Status:** decisão arquitetural proposta/aprovada para implementação.

## Contexto
Dois serviços lógicos: lançamentos e consolidado diário. A escrita de lançamentos não pode depender da disponibilidade do processamento de consolidação. O teste precisa ser executável localmente e desenvolvido rapidamente.

## Decisão
Monólito modular .NET 10, com API e Worker separados como hosts dos módulos; PostgreSQL único com schemas `transactions` e `consolidation`, DbContexts, migrations e roles independentes. Cada módulo grava exclusivamente no próprio schema. Mudanças entre módulos via eventos/comandos RabbitMQ, processados pelo proprietário. Transactions usa Outbox transacional; Consolidation usa Inbox e atualizações idempotentes. Consultas cruzadas priorizam contratos/read models, não tabelas alheias. Polly com retries limitados e circuit breaker em dependências transitórias. Consistência eventual aceita.

## Consequências positivas
Menor custo e complexidade que microsserviços; clara separação de responsabilidades; desacoplamento temporal; reprocessamento seguro; documentação demonstra trade-offs.

## Consequências negativas
PostgreSQL compartilhado continua ponto comum de falha; duplicação de mensagens possível; relatório pode estar defasado; RabbitMQ aumenta operação. API e Worker são deployables separados, portanto não alegar que existe um único processo.

## Alternativas descartadas
- Microsserviços completos: custo/complexidade excessivos para prova.
- Comunicação síncrona de Transactions para Consolidation: viola independência durante indisponibilidade.
- Atualização direta no schema alheio: viola ownership e aumenta acoplamento.
- Broker sem Outbox: risco de gravar lançamento sem evento publicável.
